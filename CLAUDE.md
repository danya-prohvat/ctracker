# CLAUDE.md — Calorie Tracker (com.prxfitness.calorietracker)

## Проєкт
- Нативний iOS-трекер калорій/макро/мікронутрієнтів. Джерело правди — спека `~/Downloads/tz-claude-code-ua.md` (укр.) + затверджений HTML-прототип; при конфлікті перемагає спека.
- **Візуальний стиль (рішення користувача 2026-07-08): Apple-нативний, не прототипний.** Прототип лишається референсом структури/розкладки екранів, але оформлення — за HIG: Dynamic Type стилі (`.headline`/`.footnote`…, НЕ `.system(size:)`), великі цифри — `Font.stat(...)` (SF Rounded, як у Health/Fitness), SF Symbols замість рукомальованих іконок, білі картки без «скла». Гляньцеві елементи/насичені пастельні градієнти прототипу не повертати.
- **Фон — «аврора» (рішення користувача 2026-07-28, замінює плаский сірий від 2026-07-08)**: `AppBackground` = нейтральна база `Theme.background` (#F5F6F5) + три м'які radial-плями `Theme.auroraGreen/auroraBlue/auroraWarm` (зелена top-leading, блакитна trailing, тепла знизу; стиль Apple Journal/Invites, кольори standalone — навмисно не прив'язані до макро-палітри). Фон скрізь ТІЛЬКИ через `AppBackground` (пейвол і онбординг теж переведені), не через голий `Theme.background`.
- **Мікро-взаємодії (рішення користувача 2026-07-28)**: кільця `ProgressRing` заповнюються пружинкою при першій появі; числа калорій/макро — `contentTransition(.numericText(value:))`; іконки табів — `symbolEffect(.bounce)` + `.sensoryFeedback(.selection)`; FAB — градієнт `fabTop→fabBottom`; успішне логування — success-хептика в `DiaryLogger.log`. Нові делайти — у цьому ж стилі: стримано, без конфеті. (Кільця Activity-градієнтом і «святкування 100%» користувач НЕ обрав 2026-07-28 — не додавати без явного прохання.)
- **Переходи екранів і списків (рішення користувача 2026-07-28)**: crossfade табів (`RootView`, `.animation` по `selectedTab`); напрямлений slide сітки календаря (`CalendarGridCard.stepDirection` + `.push`-transition, RTL-aware; перемикання week/month — fade, `stepDirection = 0`); fade фаз сканера (`ScanFlowView`, `.animation` по `phase`); вставка/видалення записів щоденника і swap empty state — `DayView` (`.animation` по `entries.count`) + transitions на `DiaryRow`/`DayEmptyStateCard`. Успішний камерний скан = `ScanFeedback.success()` (success-хептика + системний «тік» 1057) + debounce 2с того самого коду в `ScanFlowView.handleScannedCode`; ручний debug-ввід — без звуку.
- **Тактильні кнопки (рішення користувача 2026-07-28)**: спільний `Core/PressableScaleStyle.swift` — `.pressableScale` (0.92, компактні: FAB, клавіші кейпада, круглі кнопки) і `.pressableCard` (0.97, широкі CTA й кнопки-картки: Continue онбордингу/пейвола, Log/Save-бари, Add food, New product/Scan, Unlock history). Клавіші кейпада мають тап-хептику (`.sensoryFeedback(.impact(flexibility: .soft))`); фон клавіші (`glassCard`) живе всередині label, щоб стискалась уся клавіша. Нові кнопки-об'єкти зобов'язані брати один із цих стилів; рядки списків, комірки календаря і свайп-дії лишаються `.plain` (нативний iOS їх не стискає).
- **Текст у компактних кнопках (рішення користувача 2026-08-04, після бага з «Оформити Преміум» у два рядки)**: спільний `Core/TextFit.swift` — `.badgeFit()` (`lineLimit(1)` + `fixedSize`) для капсул-бейджів (Upgrade у `SettingsPremiumCard`, BEST VALUE у `PaywallPlanRow`: капсула не переноситься, замість неї wrap-ається сусідній гнучкий текст) і `.ctaFit()` (`lineLimit(1)` + `minimumScaleFactor(0.75)`) для CTA з фіксованою висотою й лейблів таб-бара (ScanActionBar, QuantityActionBar, ProductFormCTABar, PaywallView Continue, OnboardingPrimaryButton, Unlock history, FloatingTabBar, Scan-картка Add food). Нові капсули/CTA зобов'язані брати відповідний модифікатор. Друга половина правила — контент: короткі ключі-дії (кнопки) не перекладати довгими фразами; задовгі переклади вкорочено 2026-08-04 («Upgrade» ≤ ~11 симв. у fr/hu/it/pl/pt-BR/ro/ru/sk/uk, «BEST VALUE» ≤ 13 у fr/hu/it/ms/pl/ro) — нові переклади кнопок тримати в цих межах.
- Структура: `CalorieTracker/App` (entry, RootView), `Models` (@Model), `Core` (каталог нутрієнтів, математика, формат, тема), `Features/<Назва>` (по папці на фічу).
- `.xcodeproj` використовує PBXFileSystemSynchronizedRootGroup — нові файли під `CalorieTracker/` підхоплюються автоматично, pbxproj правити не треба.

## Доменні інваріанти (зі спеки, НЕ порушувати)
- **Історія незмінна**: `DiaryEntry` — знімок (frozen per-100 значення + назва) у момент логування. Редагування/видалення `Product` ніколи не змінює минулі записи. `productID` у записі — лише довідка, ніколи не для перерахунку. Це навмисна денормалізація — не «оптимізувати» її прибиранням дублювання.
- **Канонічні одиниці**: все зберігається тільки в г/мл на 100; oz/fl oz — лише ввід/відображення, конвертація через `FoodUnit.toCanonical` в момент вводу. Початкове значення `unitSystem` при першому запуску — з пристрою: `Locale.current.measurementSystem == .us` → US, решта (вкл. `.uk`) → Metric (сідується в `UserSettings.current(in:)`, рішення 2026-07-21); тумблер юнітів в онбордингу пише вибір у `settings.unitSystem` одразу. Показ теж конвертується (рішення користувача 2026-07-16): кількості — через `Format.quantity(_:basis:unitSystem:)` («34 fl oz»), лейбли основи — через `Basis.per100Label(_:)`/`per100Compact(_:)` («per 3.5 oz» — сам per-100 не перераховується, конвертується лише підпис, щоб kcal/макро поруч не спотворювались). Форма продукту дозволяє вводити значення «на X г/мл» (рішення користувача 2026-07-14): нормалізація до per-100 — при сабміті через `per100Factor` у `NewProductForm`; log-once логає кількість = X (передається через `LoggableFood.lastQuantity`).
- **День** = локальний `dayKey` рядком `"yyyy-MM-dd"` (див. `Core/DayKey.swift`), обчислюється при логуванні й зберігається в записі. Нові фічі використовують цей самий механізм. Вкладка Today тримає ключ у `@State` і оновлює його на `NSCalendarDayChanged` + активації сцени, з `.id(dayKey)` для скидання `@Query` (виправлено 2026-07-28: одноразовий `DayKey.today` у body «застрягав» у вчора через північ) — не спрощувати назад. Обидва сигнали інкапсульовано в `Core/OnDayChange.swift` (`.onPossibleDayChange`); Calendar-таб так само тримає `todayKey` у `@State` і на зміні дня оновлює маркер «сьогодні» + refetch (виправлено 2026-08-04: `let todayKey = DayKey.today` у рендері `CalendarGridCard` застрягав у вчора, новий день лишався disabled). Нові «сьогодні»-залежні екрани зобовʼязані використовувати цей модифікатор, не разовий `DayKey.today` у body.
- **Freemium**: клітковина, цукор, натрій і насичені жири завжди безкоштовні та ввімкнені за замовчуванням (рішення користувача 2026-07-08, ширше за спеку §4; набір = `PremiumGate.freeNutrientIDs` = `NutrientCatalog.defaultEnabled`); сканер — 10 безкоштовних **успішних** сканів (рішення користувача 2026-08-03, замінює 3 зі спеки §9): лічильник тікає ЛИШЕ коли скан знайшов новий продукт через OFF; повторний скан продукту, що вже є в базі (локальний хіт), — безкоштовний і без реклами; not found/denied теж не рахуються (`AddFoodScanFlow`); історія глибше 30 днів — преміум. Єдина точка перевірки — `PremiumGate`. Базове логування їжі НІКОЛИ не блокувати.
- **30-денний замок історії — «чесний замок»** (рішення користувача 2026-07-12): у календарі дні поза вікном (`!PremiumGate.isDayUnlocked`) рендеряться з іконкою замка без кільця (`CalendarDayCell.isLocked`), тап → пейвол. Кільця й середні (`kcalByDay`, `periodStats`) рахуються ТІЛЬКИ по розблокованих днях — агрегати заблокованих днів не «підглядаються». Повністю заблокований період → замість `CalendarStatsRow` показуємо `CalendarHistoryLockedCard` (CTA на апгрейд). Навігація по старих місяцях лишається дозволеною (видно «скільки історії за замком»). Вікно = останні 30 днів включно, єдине джерело — `PremiumGate.isDayUnlocked`.
- **Набір трекованих нутрієнтів — per-day, історія незмінна** (рішення користувача 2026-07-12): `enabledNutrients` — це лише «поточний» набір; фактичний набір для конкретного дня береться з журналу змін `UserSettings.nutrientTrackingLog` (`[NutrientTrackingChange]`, див. `Core/NutrientTrackingLog.swift`). День-детейл (`DayView`→`DaySummaryCard`→`VitaminsMineralsSection`) показує нутрієнти, ввімкнені **на той день**, через `enabledNutrientDefs(on: dayKey)`, а не глобальний список. Правило запису: перемикання нутрієнта → `ensureNutrientTrackingBaseline()` (сід floor-точки `DayKey.beginning` з попереднім набором) перед мутацією, потім `recordNutrientTrackingChange()` (upsert точки на сьогодні) — минулі дні НІКОЛИ не переписуються. Порожній журнал (legacy-інстали) → фолбек на живий `enabledNutrients`. Знімки `DiaryEntry.per100Micros` і далі містять УСІ мікронутрієнти незалежно від ввімкнення — «ввімкнено» керує лише відображенням/цілями, не даними. **Преміум-політика**: гейт стоїть на *ввімкненні* (`PremiumGate.isNutrientUnlocked`), а не на відображенні; після втрати преміуму історичні дні й далі показують преміум-нутрієнти, які тоді трекались (форвард обмежується безкоштовним набором). НЕ гейтити нутрієнти на рівні показу історії й не прибирати журнал змін заради «дедуплікації».

## SwiftData: правила CloudKit-сумісності (ОБОВ'ЯЗКОВО)
Порушення будь-якого з цих правил зламає майбутню синхронізацію:
1. НІКОЛИ не використовувати `@Attribute(.unique)` і `#Unique`. Дедуплікація (напр., продукт за barcode) — тільки в коді через fetch-перед-insert. Для продуктів це `Core/ProductStore.swift` (`existing`/`upsert`) — єдина точка «один штрихкод = один продукт»; нові шляхи збереження продуктів мусять іти через нього, не через голий `context.insert`.
2. Кожна не-optional властивість @Model мусить мати дефолтне значення: `var calories: Double = 0`.
3. Усі relationships — optional (`var meal: Meal?`) або з дефолтом `= []`, з явним `inverse:` в `@Relationship`.
4. Не використовувати deleteRule `.deny` (CloudKit його не підтримує). Тільки `.cascade` / `.nullify`.
5. Не покладатися на порядок у to-many relationship — CloudKit його не гарантує. Зберігати явний `sortOrder: Int` або сортувати за датою.
6. Batch-операції (`context.delete(model:)` тощо) обходять CloudKit-export — зміни, які мають синкатись, робити тільки по-об'єктно (fetch + `context.delete(object)`); так уже зроблено в «Delete all data» (`SettingsDeleteCard`, виправлено 2026-07-28).

## SwiftData: загальні практики
- `FetchDescriptor` завжди з `#Predicate` і, де можливо, `fetchLimit` — не тягнути всю таблицю в пам'ять (щоденник за рік = тисячі записів).
- Запити для UI — через `@Query` у view з предикатом на поточний день/період, а не фільтрація масиву в `body`.
- Важкі операції (імпорт продукту з Open Food Facts/USDA, batch-обробка) — через `@ModelActor` на фоні, не через `mainContext`.
- Фото їжі та інші blob'и — не в базу напряму: `@Attribute(.externalStorage)` або файли в Application Support з шляхом у моделі.
- Версіонування схеми з першого релізу: `VersionedSchema` + `SchemaMigrationPlan`, навіть якщо зараз одна версія. Будь-яка зміна @Model після релізу = нова версія схеми + міграція.
- Enum-и в @Model зберігати через приватне `*Raw`-поле (String/Int) з computed-обгорткою — так уже зроблено в `Product.basisRaw` тощо.
- `UserSettings` — синглтон через `UserSettings.current(in:)` (fetch-or-create); не створювати другий екземпляр.

## Модель нутрієнтів (37 нутрієнтів)
- Каталог — статичний `NutrientCatalog.all` (стабільні `id`, одиниці, дефолтні норми, групи). Нові нутрієнти — тільки туди; `id` після релізу не змінювати (це ключі в збережених словниках).
- Всі значення зберігати нормалізовано на 100 г/мл продукту (`Double`), розрахунок на порцію — в runtime, не дублювати в базі. (Виняток — снапшоти в `DiaryEntry`, див. «Доменні інваріанти».)
- Одиниці — через enum з метаданими (g / mg / µg / kcal), конвертація тільки в одному місці (helper), не «магічні ×1000» по коду.
- Відображення чисел — тільки locale-aware, через `Core/Format.swift` (єдина точка форматування/парсингу). Ніколи `String(format:)` з хардкодом крапки (укр/араб. локалі мають інші роздільники).
- **Один знак після коми глобально (рішення користувача 2026-07-16, замінює «цілі числа» від 2026-07-14)**: увесь числовий ввід і показ — максимум 1 десятковий знак. `Format.amount`/`kcal`/`editable` форматують з `maximumFractionDigits = 1`, `Format.parse` округляє до 0.1 (`Format.round1`), числові TextField-и — `.decimalPad`, кастомний кейпад кількості має клавішу роздільника (`QuantityKey.separator`, лейбл — locale-aware `Locale.current.decimalSeparator`). Цілі значення показуються без «.0». Дані в моделях лишаються `Double`; округлення — тільки на межі вводу/показу.
- **Ліміт величини вводу (рішення користувача 2026-07-14)**: кожне числове поле обмежує ввід через `.numericInputLimit(_:maxDigits:)` (`Core/NumericInputLimit.swift`): `maxDigits` цифр цілої частини (дефолт 4 → 9999) + не більше одного десяткового знака (санітайзер — `NumericInput.limited`, приймає «.», «,» і арабський десятковий «٫» U+066B — виправлено 2026-07-28: без нього ar-локаль множила дроби на 10, бо `isNumber` пропускає арабські цифри, а роздільник викидався; `Format.parse` має той самий «٫»-фолбек). Поля форми продукту й «Per» — 4, ціль ккал — 5, калькулятор цілей — 3; кейпад кількості кляпає так само сам (`QuantityEditor.maxDigits` + `NumericInput.limited` на префілі). Нові числові поля зобов'язані вішати цей модифікатор.
- Відсутній нутрієнт ≠ 0: у словниках `micros`/`per100Micros` відсутній ключ = «немає даних», показувати «—». Не записувати 0 замість відсутнього значення — зіпсуються агрегати за день.
- Семантика цілі — `NutrientDef.kind`: `goal` («добери до 100%», перевищення = успіх, чекмарк) або `limit` («не перевищуй»: ≥90% — amber `Theme.warning`, >100% — red + текстове «+X over», ніколи не лише кольором). Фіксується в каталозі, юзер не редагує. Ліміти: sodium, sugar, saturatedFat, transFat, cholesterol, caffeine. **Кольори goal-progress індикаторів — два патерни (рішення користувача 2026-07-21, уточнює 2026-07-10)**: (1) ретроспективні поверхні — кільця днів у календарі (`CalendarDayCell`) і прогрес-смужки статистики (`CalendarStatsRow`) — використовують нейтральний `CalendarRingState` (недобір — сірий, у нормі — зелений, перебір — amber `Theme.warning`); (2) «живі» кільця поточного дня на Today — головне кільце калорій (`CalorieRingView`) і макро-кільця (`MacroRingsView`) — використовують `TodayRingStyle` (`Features/Today/TodayRingStyle.swift`): дуга в акцентному кольорі (калорії — `Theme.accent`, макро — `Theme.protein`/`fat`/`carbs`), трек — той самий колір з opacity 0.18 (Fitness-стиль, кільце ніколи не «сіре й вимкнене»), перебір >105% → дуга й трек amber. Поріг перебору спільний — `CalendarRingState.overThreshold`. **Ніколи не червоний** — демотивація червоним заборонена в обох патернах.

## SwiftUI (iOS 17 ідіоми)
- Поточна архітектура — прості view + `@State` + `@Query`, без view-моделей. Якщо з'являється спільний стан/логіка — `@Observable` макрос (НЕ `ObservableObject`/`@Published`). `@State` для володіння, `@Environment` для ін'єкції.
- `NavigationStack` з типізованим path/enum-роутером або `navigationDestination(item:/isPresented:)`; модальні кроки й alerts — через `@State` item-биндинги (напр. `AddSheet` в AddFood).
- Ніяких `AnyView` без крайньої потреби; великі view розбивати на підструктури.
- Асинхронність: `.task {}` (з автоскасуванням), не `onAppear + Task`.
- Preview для кожного екрана з in-memory контейнером: використовувати готовий `PreviewData.container` з мок-даними.
- Doubles/units в UI — `Measurement` + `.formatted()` де доречно.

## Локалізація та RTL (en/uk/ru/ar)
- Усі юзер-фейсинг рядки — через `LocalizedStringKey` (у View) або `String(localized:)` (поза View). НІКОЛИ голий `String` у Text для UI-тексту.
- Не конкатенувати рядки (`"Всього: " + value`) — тільки інтерполяція `Text("Всього: \(value)")`, інакше String Catalog потім не витягне їх коректно.
- Ключі писати так, щоб пізніше автоматично екстрактнулися у `.xcstrings` без правок коду.
- RTL: тільки `.leading`/`.trailing`, ніколи `.left`/`.right`; не хардкодити напрямок HStack; кастомні іконки зі «стрілочною» семантикою — перевіряти flip. Тестувати preview з `.environment(\.layoutDirection, .rightToLeft)` і `.environment(\.locale, Locale(identifier: "ar"))`.
- Плюрали (дні, порції) — через inflection/локалізовані формати, не `count == 1 ? ... : ...`.

## Сканер штрихкодів (AVFoundation)
- `NSCameraUsageDescription` вже задано через `INFOPLIST_KEY_...` у build settings — не дублювати в окремому Info.plist.
- `AVCaptureSession` запускати/зупиняти на власній serial queue, ніколи на main.
- Metadata types: `.ean13`, `.ean8`, `.upce`, `.code128`. UPC-A приходить як EAN-13 з провідним нулем — lookup пробує обидві форми через `BarcodeNormalizer.candidates` (зроблено 2026-08-03: і OFF-запит у `BarcodeLookupService.lookup`, і локальний пошук `ProductStore.existing(scannedCode:)`; префіл несе код, за яким продукт реально знайшовся).
- Debounce повторних спрацювань того самого коду (~2с), haptic + звук на успіх, після успіху — зупиняти сесію.
- Закриття сканера скасовує активний OFF-lookup (виправлено 2026-08-04): хендл у `ScanFlowView.lookupTask` + `.onDisappear { cancel() }`, у Task — `guard !Task.isCancelled` після await і в catch. Без цього пізня відповідь показувала rewarded-рекламу поверх Add food, списувала безкоштовний скан за небачений результат і лишала застарілий `pendingScan`. Додатковий пояс: `startScan()` чистить `pendingScan` перед відкриттям кавера. Не замінювати `lookupTask` на голий `Task {}`.
- Відмова в доступі до камери: не глухий кут, а екран з поясненням і кнопкою в Settings (`UIApplication.openSettingsURLString`) — уже реалізовано у `ScanFlowView`, фаза `.denied`.
- На симуляторі камери немає — зберігати debug-панель ручного вводу коду.

## Мережа (Open Food Facts)
- OFF вимагає кастомний `User-Agent` виду `CalorieTracker/1.0 (com.prxfitness.calorietracker; contact@utr.ua)` — без нього можливий бан.
- Порядок: спершу локальна база (вже сканували) → OFF. Знайдений продукт зберігати локально, повторний скан = офлайн.
- **USDA-fallback прибрано на прохання користувача 2026-07-12** (OFF покриває цільові ринки — перевірено на румунських товарах; USDA дає лише продукти ринку США). Не повертати без явного прохання; безкоштовний ключ FDC за потреби видається за 2 хв на fdc.nal.usda.gov.
- ODbL-атрибуція Open Food Facts обов'язкова скрізь, де показуються їхні дані (уже є футер у ScanFlowView — не прибирати).
- Моделі відповідей — толерантні до null/відсутніх полів (все optional, числа можуть приходити рядками), OFF-дані брудні.
- Помилки мережі — типізований enum + зрозумілий стан у UI (retry), не мовчазний фейл і не `try!`. «Не знайдено» ≠ помилка мережі — це різні стани UI.
- API-ключі — тільки в конфіг-структурах (`PurchasesConfig`, `AdsConfig`), не розкидати по коду. **Публічні** ключі, які й так шипляться в бінарнику (RevenueCat public key `appl_…`, AdMob unit ID), можуть жити в коді й комітитися (рішення користувача 2026-08-03, уточнює правило від 2026-07-14); **секретні** ключі (server keys, приватні токени) — окремий конфіг-файл у `.gitignore`.

## Нотифікації (нагадування)
- **Розумні нагадування (рішення користувача 2026-07-19)**: рівно дві локальні нотифікації на день, схема фіксована (юзер має лише тумблер on/off у Settings → General). 14:00 — тільки якщо за день ще нічого не залогано; 20:00 — нічого не залогано → «залогай», залогано < 80% цілі калорій → «лишилось X kcal», ≥ 80% (або ціль не задана) → мовчати. Вся логіка — `Core/MealReminderScheduler.swift`: планує вікно 7 днів наперед (майбутні дні = варіанти «нічого не залогано») і повністю перепланує на кожній зміні `scenePhase` (active/background) у `RootView` — логування можливе лише в застосунку, тож розклад не встигає застаріти. НЕ повертати ручні часи нагадувань (`SettingsRemindersView`/`reminderTimesMinutes` видалено 2026-07-19); легасі-ідентифікатори `settings.mealReminder.*` чистяться при кожному переплануванні.
- **Re-engagement серія (рішення користувача 2026-07-19)**: 6 нотифікацій «повернись у застосунок» на дні 2/4/7/14/21/31 після останнього відкриття, о 12:00 (виняток: день 14 на Сб/Нд з'їжджає на наступний Пн 9:00). Логіка — `Core/ReengagementNotificationService.swift`: на кожній активації (`scenePhase == .active` у RootView) вся серія скасовується і плануться заново від «зараз» — нотифікація спрацьовує лише якщо застосунок реально не відкривали. Ідентифікатори стабільні `reengagement.day2`…`reengagement.day31`. Дозвіл НІКОЛИ не питає (планує тільки при .authorized/.provisional, інакше мовчки нічого). Тумблер — СПІЛЬНИЙ `UserSettings.notificationsEnabled` (рішення користувача 2026-07-21: один свічер «Reminders» у Settings → General керує і смарт-нагадуваннями, і re-engagement серією; окремий рядок «Comeback reminders» і властивість `reengagementNotificationsEnabled` видалені — НЕ повертати); off → скасування обох. «Delete all data» теж скасовує обидві серії. Тексти — ключі `reengagement_day2`…`_day31` у `Localizable.xcstrings` (title порожній — iOS показує назву застосунку). DEBUG-тест: Settings → Test → «Test re-engagement (minutes)» (`scheduleTestSeriesMinutes` — день N = N хвилин).
- Мова текстів нотифікацій (2026-08-04): обидва планувальники будують рядки через `String(localized:bundle:)` з `AppLanguage.bundle(for: settings.languageCode)` — нотифікації приходять мовою, обраною в застосунку, ще до рестарту процесу; зміна мови (`SettingsGeneralCard.apply`) одразу перепланує обидві серії. Нові тексти нотифікацій зобов'язані йти через цей бандл, не через голий `String(localized:)`.
- Дозвіл питати в контексті — коли юзер вмикає тумблер нагадувань, не на першому запуску. При статусі `.denied` тумблер НЕ «мовчки відскакує»: `SettingsGeneralCard` спершу питає `MealReminderScheduler.authorizationStatus`, і для denied показує алерт з кнопкою Open Settings (`openSettingsURLString`) — той самий стандарт, що для камери в сканері (виправлено 2026-08-03).
- Ідентифікатори нотифікацій — детерміновані з неймспейсом (як `smartReminder.afternoon.<dayKey>`), щоб оновлення = заміна, а не дублікат.
- Після зміни налаштувань/стану — `removePendingNotificationRequests` для старих id, потім планувати нові.
- Debug-перегляд запланованих: Settings → Test → Scheduled notifications (`PendingNotificationsSheet`, `#if DEBUG`).

## Принципи коду (KISS / SOLID / DRY)
- Файл — не більше 200 рядків. Наближається до ліміту → виносити підв'юхи, extension'и, helper'и в окремі файли, а не «дотискати».
- KISS: найпростіше рішення, яке працює. Ніяких абстракцій «на майбутнє», generic-протоколів заради одного конформера, менеджерів-обгорток над системними API без реальної потреби.
- DRY: логіка, що повторюється ≥2 рази (конвертація одиниць, форматування нутрієнтів, розрахунок денних сум) — виноситься в один helper/extension. Але не DRY-ити випадкові збіги: два схожі view з різною долею — це два view.
- SOLID (прагматично для SwiftUI):
  - S: view малює, `@Observable`-стор тримає стан і логіку, сервіс (мережа/сканер/нотифікації) робить одну справу. Не змішувати в одному типі.
  - O/D: view і стори залежать від протоколів сервісів (`PurchaseService` як protocol — уже так), конкретні реалізації (OFF, USDA, мок для preview) — окремо.
  - I: вузькі протоколи (`BarcodeScanning`, `NotificationScheduling`), а не один жирний `AppService`.
- Не плодити шари заради шарів: якщо view-логіки на 3 рядки — їй не потрібен окремий ViewModel.

## Загальний код-стайл
- Swift Concurrency: `async/await`, UI-код `@MainActor`; `DispatchQueue` — тільки там, де вимагає API (AVCapture).
- Ніяких `!` force unwrap, `try!`, `as!` у продакшн-коді.
- Дати/календар: завжди `Calendar.current` з урахуванням time zone юзера; «день» у щоденнику — локальний день через `DayKey`. Виняток: сам `DayKey` навмисно форматує ключ через фіксований gregorian + `en_US_POSIX` — ключ зберігання має бути стабільним незалежно від локалі/календаря юзера, не «виправляти» це на `Calendar.current`.
- Нові файли: один основний тип на файл, назва файлу = назва типу.
- DEBUG launch-аргументи: `-seedSample 1` (сід даних у порожній стор), `-skipOnboarding 1`, `-resetOnboarding 1`, `-initialTab calendar|settings`. Нові debug-хуки — тільки під `#if DEBUG`.
